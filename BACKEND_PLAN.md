# План реализации бэкенда

## Цель

Сделать бэкенд для "Журнала работ на строительном объекте" на `Node.js + TypeScript + NestJS` с сохранением данных в базе и API для фронтенда на React.

Бэкенд должен покрывать обязательные требования тестового задания:

- хранение записей журнала в БД;
- получение списка записей;
- фильтрация и/или сортировка по дате;
- создание записи;
- редактирование записи;
- удаление записи;
- использование справочника видов работ вместо свободного ввода.

## Предлагаемый стек

- `Node.js`
- `TypeScript`
- `NestJS`
- `PostgreSQL` как основная БД
- `Prisma ORM` для работы с БД и миграций
- `class-validator` и `class-transformer` для валидации DTO
- `Docker Compose` для локального запуска и простого деплоя на сервер
- `Swagger` для документации API

## Почему такой выбор

- `NestJS` хорошо подходит для тестовых и production-like сервисов: понятная модульность, DI, DTO, guards/interceptors при необходимости.
- `PostgreSQL` надежен, привычен для CRUD-сценариев и хорошо подходит под дальнейшее развитие.
- `Prisma` ускоряет разработку: удобные миграции, типобезопасный клиент, простая работа со связями.
- `Swagger` упростит проверку задания и ручное тестирование API.
- `Docker Compose` снизит порог запуска для проверяющего и подойдет как базовый способ развертывания на своем сервере, если не нужен Kubernetes или более сложная инфраструктура.

## Границы первой версии

В первой версии делаем один сервис без авторизации и без сложной доменной логики.

Не включаем в MVP:

- роли и права доступа;
- аудит изменений;
- вложения, фото, акты;
- сложные статусы согласования;
- несколько объектов строительства;
- пагинацию как обязательную часть, если объем данных маленький.

Если останется время, это можно добавить позже.

## Доменная модель

### 1. Запись журнала работ

Сущность `work_log_entries`:

- `id` - UUID
- `workDate` - дата выполнения работ
- `workTypeId` - ссылка на вид работ
- `measurementUnitId` - ссылка на единицу измерения
- `volume` - числовой объем
- `workerName` - ФИО исполнителя
- `createdAt`
- `updatedAt`

### 2. Вид работ

Сущность `work_types`:

- `id` - UUID
- `name` - название вида работ
- `createdAt`
- `updatedAt`

Примеры начальных значений:

- `Кладка перегородок`
- `Монтаж опалубки`
- `Армирование`
- `Бетонирование`
- `Штукатурные работы`

### 3. Единица измерения

Сущность `measurement_units`:

- `id` - UUID
- `name` - полное название, например `кубический метр`
- `symbol` - краткое обозначение, например `м3`
- `createdAt`
- `updatedAt`

Примеры начальных значений:

- `штука` / `шт`
- `квадратный метр` / `м2`
- `кубический метр` / `м3`
- `погонный метр` / `п.м.`

## Схема базы данных

### Таблица `work_types`

- `id uuid primary key`
- `name varchar not null unique`
- `created_at timestamp not null default now()`
- `updated_at timestamp not null default now()`

### Таблица `work_log_entries`

- `id uuid primary key`
- `work_date date not null`
- `work_type_id uuid not null references work_types(id)`
- `measurement_unit_id uuid not null references measurement_units(id)`
- `volume numeric(10,2) not null`
- `worker_name varchar(255) not null`
- `created_at timestamp not null default now()`
- `updated_at timestamp not null default now()`

### Таблица `measurement_units`

- `id uuid primary key`
- `name varchar(100) not null unique`
- `symbol varchar(20) not null unique`
- `created_at timestamp not null default now()`
- `updated_at timestamp not null default now()`

### Индексы

- индекс на `work_date`
- индекс на `work_type_id`
- индекс на `measurement_unit_id`

Это даст нормальную основу для фильтрации по дате и выборок по виду работ.

## API-контракты

### 1. Получить список записей

`GET /work-log-entries`

Параметры query:

- `dateFrom` - необязательно
- `dateTo` - необязательно
- `sortBy` - например `workDate`
- `sortOrder` - `asc | desc`

Пример:

`GET /work-log-entries?dateFrom=2026-05-01&dateTo=2026-05-31&sortBy=workDate&sortOrder=desc`

Ответ:

```json
[
  {
    "id": "uuid",
    "workDate": "2026-05-25",
    "volume": 24,
    "workerName": "Иванов И.И.",
    "workType": {
      "id": "uuid",
      "name": "Монтаж опалубки"
    },
    "measurementUnit": {
      "id": "uuid",
      "name": "кубический метр",
      "symbol": "м3"
    },
    "createdAt": "2026-05-25T10:00:00.000Z",
    "updatedAt": "2026-05-25T10:00:00.000Z"
  }
]
```

### 2. Получить одну запись

`GET /work-log-entries/:id`

Нужно для экрана редактирования или детального просмотра.

### 3. Создать запись

`POST /work-log-entries`

Тело запроса:

```json
{
  "workDate": "2026-05-25",
  "workTypeId": "uuid",
  "measurementUnitId": "uuid",
  "volume": 24,
  "workerName": "Иванов И.И."
}
```

### 4. Обновить запись

`PATCH /work-log-entries/:id`

Тело запроса:

```json
{
  "volume": 26,
  "workerName": "Петров П.П."
}
```

### 5. Удалить запись

`DELETE /work-log-entries/:id`

### 6. Получить справочник видов работ

`GET /work-types`

Ответ:

```json
[
  {
    "id": "uuid",
    "name": "Кладка перегородок"
  }
]
```

### 7. Получить справочник единиц измерения

`GET /measurement-units`

Ответ:

```json
[
  {
    "id": "uuid",
    "name": "кубический метр",
    "symbol": "м3"
  }
]
```

## Правила валидации

### Для создания записи

- `workDate` обязательно, корректный формат даты
- `workTypeId` обязательно, должен существовать в БД
- `measurementUnitId` обязательно, должен существовать в БД
- `volume` обязательно, число больше нуля
- `workerName` обязательно, строка длиной до 255 символов

### Для обновления записи

- все поля необязательные;
- если поле передано, оно должно проходить те же проверки, что и при создании.

### Дополнительные бизнес-проверки

- нельзя создать запись с несуществующим `workTypeId`;
- нельзя создать запись с несуществующим `measurementUnitId`;
- при запросе/обновлении/удалении несуществующей записи возвращать `404`;
- при невалидных данных возвращать `400`.

## NestJS-модули

### `DatabaseModule`

Отвечает за абстракцию доступа к базе данных.

Внутри первой версии:

- инкапсулирует подключение Prisma Client;
- экспортирует database service для модулей приложения;
- изолирует ORM-детали от остальной структуры проекта.

Такой нейминг лучше, чем `PrismaModule`, потому что не привязывает архитектуру верхнего уровня к конкретной ORM. Если позже захотим заменить Prisma или добавить дополнительные адаптеры, внешний контракт модуля будет уже готов.

### `WorkTypesModule`

Содержит:

- контроллер для чтения справочника видов работ;
- сервис для получения списка видов работ;
- при необходимости метод сидирования стартовых значений.

### `MeasurementUnitsModule`

Содержит:

- контроллер для чтения справочника единиц измерения;
- сервис для получения списка единиц измерения;
- сидирование стартовых значений.

### `WorkLogModule`

Содержит:

- контроллер CRUD для записей журнала;
- сервис с бизнес-логикой;
- DTO для create/update/query;
- маппинг ответа API.

## Основные сценарии реализации

### Сценарий 1. Просмотр списка

1. Фронтенд вызывает `GET /work-log-entries`.
2. Бэкенд принимает query-параметры фильтрации и сортировки.
3. DTO валидирует входные параметры.
4. Service собирает Prisma query.
5. Возвращается список записей вместе с названием вида работ.

### Сценарий 2. Создание записи

1. Фронтенд отправляет форму на `POST /work-log-entries`.
2. DTO валидирует тело запроса.
3. Service проверяет существование `workTypeId`.
4. Service проверяет существование `measurementUnitId`.
5. Создается запись в БД.
6. Возвращается созданная сущность.

### Сценарий 3. Редактирование записи

1. Фронтенд отправляет `PATCH /work-log-entries/:id`.
2. Service проверяет, существует ли запись.
3. Если меняется `workTypeId`, отдельно проверяется его существование.
4. Если меняется `measurementUnitId`, отдельно проверяется его существование.
5. Выполняется обновление.
6. Возвращается обновленная запись.

### Сценарий 4. Удаление записи

1. Фронтенд вызывает `DELETE /work-log-entries/:id`.
2. Service проверяет существование записи.
3. Запись удаляется.
4. Возвращается `204 No Content`.

## Обработка ошибок

Нужно сразу сделать предсказуемое поведение API:

- `400 Bad Request` для ошибок валидации;
- `404 Not Found` если запись или вид работ не найдены;
- `500 Internal Server Error` для неожиданных сбоев.

Можно использовать:

- глобальный `ValidationPipe`;
- стандартные `NotFoundException`, `BadRequestException`;
- при желании общий exception filter для единообразного формата ошибок.

## Сидирование данных

Для справочников видов работ и единиц измерения удобно сделать `seed`-скрипт.

Что он делает:

- заполняет `work_types` стартовыми значениями;
- заполняет `measurement_units` стартовыми значениями;
- не создает дубликаты при повторном запуске.

Это важно, чтобы после старта проекта UI сразу мог показать оба выпадающих списка.

## Решение по единицам измерения

Единицы измерения делаем отдельным справочником.

Почему это уместно:

- данные будут консистентнее;
- фронтенд получит готовый список для выбора;
- в БД не будет расхождений вроде `м2`, `м^2`, `кв.м`;
- решение лучше масштабируется, если появятся отчеты и агрегации.

## Решения, которые помогут на защите задания

- использовать UUID вместо автоинкремента;
- добавить Swagger;
- сделать сидирование справочников;
- отдать в ответе записи вложенный объект `workType`, а не только `workTypeId`;
- отдать в ответе записи вложенный объект `measurementUnit`, а не только `measurementUnitId`;
- использовать миграции, а не создавать таблицы вручную;
- приложить понятный `README.md` с запуском в 1-2 команды.

## Риски и места, где важно не переусложнить

- не стоит сразу делать сложную DDD-архитектуру;
- не нужно дробить модули сильнее, чем требует объем задания;
- не нужно добавлять авторизацию, если ее не просят;
- не нужно преждевременно строить универсальный фильтр по всем полям.

Главная цель - аккуратный, понятный, рабочий CRUD-сервис.
